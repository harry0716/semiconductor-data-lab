# 自判斷修改診斷原則

## 1. 目的

本文件規範代理在開發與修正問題時的診斷流程。代理不得看到錯誤就直接局部修補，必須先分類問題、確認根因，再做最小充分修改。

## 2. 問題分類

### A 類：規格問題

現象：

- 功能與教學目標不一致。
- 規格互相矛盾。
- 流程缺少必要步驟。
- 使用者角色不清楚。

處理：

- 先修改規格。
- 不用程式 workaround 掩蓋規格問題。
- 必要時提交人工審查。

### B 類：架構問題

現象：

- 模組高度耦合。
- 修改一處導致多處失效。
- 部署方式被寫死。
- 資料狀態無法重現。

處理：

- 先修正模組邊界或介面。
- 禁止大量新增條件判斷暫時繞過。

### C 類：資料問題

現象：

- 測試資料與 schema 不符。
- 參考答案不一致。
- 亂數生成不可重現。
- 分析結果不具意義。

處理：

- 區分資料生成錯誤與分析函式錯誤。
- 由獨立驗證代理重算結果。

### D 類：實作缺陷

現象：

- 函式邏輯錯誤。
- UI 狀態錯誤。
- API 回傳錯誤。
- 權限驗證遺漏。

處理：

- 建立可重現測試。
- 先使測試失敗。
- 修改程式。
- 確認測試通過。
- 執行相關回歸測試。

### E 類：環境或部署問題

現象：

- 本機可執行，容器失敗。
- 環境變數缺失。
- 作業系統差異。
- 檔案路徑錯誤。

處理：

- 不得寫死平台路徑。
- 修正環境抽象層。
- 至少在本機與容器環境驗證。

### F 類：效能問題

現象：

- 大檔案導致記憶體耗盡。
- 圖表載入過慢。
- 報告生成阻塞。
- API 超時。

處理：

- 先量測瓶頸。
- 不憑感覺最佳化。
- 優先採分頁、抽樣、聚合或背景工作。

### G 類：安全問題

現象：

- 上傳檔案可繞過。
- 權限可越權。
- 輸入未驗證。
- 日誌洩漏資訊。

處理：

- 視為高優先級。
- 先封鎖危險路徑。
- 補安全測試。
- 執行同類型全域檢查。

## 3. 修改前必答問題

每次修改前，代理必須確認：

1. 問題可否穩定重現？
2. 問題屬於哪一類？
3. 根因在哪一層？
4. 是否已有測試覆蓋？
5. 修改會影響哪些模組？
6. 是否會改變 API 或資料格式？
7. 是否需要資料庫遷移？
8. 是否影響部署？
9. 是否影響原版本？
10. 是否需要更新文件？

## 4. 禁止的修改方式

禁止：

- 未重現問題就修改。
- 只處理表面錯誤訊息。
- 為單一測試硬編碼特例。
- 大範圍重構但無測試。
- 未檢查原版本就修改共享檔案。
- 因測試失敗而刪除測試。
- 因型別錯誤而全面關閉型別檢查。
- 因安全檢查失敗而停用安全機制。
- 以假資料讓測試表面通過。
- 未更新文件就改變 API。
- 未產生資料庫遷移就直接修改 schema。

## 5. 最小充分修改原則

修改應同時滿足：

- 解決根因。
- 修改範圍可控。
- 保持既有正確行為。
- 有測試證明。
- 有回歸驗證。
- 有文件更新。
- 不引入額外耦合。

最小修改不代表只改一行，而是以最小架構代價完整解決根因。

## 6. 停止自動修改條件

遇到以下情況，代理不得自行決定重大方向：

- 需要改變教學目標。
- 需要刪除已確認功能。
- 需要改變資料保存方式。
- 需要更換主要技術棧。
- 需要修改既有版本。
- 需要加入外部付費服務。
- 需要改變使用者隱私或權限模型。
- 需要大幅增加部署成本。
- 需求存在兩種以上合理但互斥方向。

此時需整理：

- 問題。
- 選項。
- 優缺點。
- 建議。
- 影響範圍。

再提交人工審查。

## 7. 完成定義

一項功能只有同時滿足以下條件才算完成：

- 規格明確。
- 程式碼完成。
- 型別檢查通過。
- 單元測試通過。
- 整合測試通過。
- 權限檢查完成。
- 錯誤處理完成。
- 日誌完成。
- 文件更新。
- 部署環境驗證。
- 教學設計驗證。
- 不影響原版本。
